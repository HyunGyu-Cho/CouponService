# V4 부하 테스트 결과

이 문서는 두 부분으로 나뉜다. 앞부분은 V3에 남은 DB 행 경합 문제를 재현한 실험이고, 뒷부분은 V4 Redis 구현 후 같은 조건에서 비교한 결과다. 뒷부분은 V4 구현 뒤에 채운다.

## 1부. 문제 재현: V3 지속 부하 실험

### 실험 개요

- 실험일: 2026-09-15
- 대상 구현: `coupon.service.v3.V3CouponIssueService` (`coupon.issue.version=v3`)
- 부하 도구: k6 v2.2.0, `load-tests/k6/coupon-issue-sustained.js` (`constant-arrival-rate`, 30초)
- 관측 도구: `load-tests/snapshot.ps1` (Actuator HikariCP 지표, MariaDB `Innodb_row_lock%`)
- 애플리케이션: Spring Boot 4.1.1, Tomcat 기본 스레드 200, HikariCP 기본 풀 10
- 데이터베이스: MariaDB 12.3
- 실행 환경: 애플리케이션, MariaDB, k6를 동일한 Windows 로컬 환경에서 실행

목적은 [V4 개발 가이드](development-guide.md) "문제"에 정의한 재현 성공 기준을 도착률을 올려 가며 확인하는 것이다.

### 조건

- 쿠폰 하나(ID 63), 재고 1,000,000. 실험 전체에서 매진되지 않아 모든 요청이 실제로 `coupon` 행을 갱신한다.
- 도착률 100, 200, 400(2회), 800, 1,600 req/s. 각 30초.
- 사용자 ID는 실행마다 `USER_ID_OFFSET`으로 구간을 나눠 중복 발급 경로에 들어가지 않는다.
- 각 실행 전후에 `snapshot.ps1`로 HikariCP와 `Innodb_row_lock%`를 찍고, 실행 중에는 1초 간격으로 `active`와 `pending`을 관찰했다.
- `Innodb_row_lock_waits`와 `Innodb_row_lock_time`은 DB 기동 이후 누적값이므로 전후 차이만 사용한다.
- 턴 종료 자동 검사의 테스트 실행이 겹치지 않았음을 테스트 결과 파일의 시각으로 확인했다.

모든 실행에서 HTTP 500은 0건이고, 실험 종료 후 쿠폰 63의 `consistency_gap`은 0이었다 (`issue_count` 93,540, `remaining_quantity` 906,460).

도착률 100 실행은 애플리케이션 재시작 후 첫 부하라 예열 효과가 섞여 있다. 잠금 대기 668회와 순간 `pending` 2는 200 실행에서 사라졌으므로 예열로 본다.

### 관찰 1. 정상 상태는 800 req/s까지 문제가 없다

200에서 800까지 중앙값 3.3~3.6ms, p95 4~7ms로 도착률과 무관하게 일정하다. DB 커넥션은 평균 1~3개만 사용됐다. 요청 하나가 3ms 안에 끝나므로 초당 800건이 들어와도 동시에 처리 중인 요청은 평균 3개가 안 된다.

행 잠금 대기 비율은 800에서 23%까지 올랐지만 대기당 1.3ms로 짧아 응답시간에 드러나지 않았다.

### 관찰 2. 800과 1,600 사이에서 포화된다

1,600 req/s 실행은 시작 9초 뒤부터 30초 내내 다음 상태였다.

```text
HikariCP: active=10 (전부 사용), pending=188~189
Tomcat:   스레드 200개 전부 점유 = DB 사용 10 + 커넥션 대기 189 + 1
k6:       VU 900개 전부 사용 (상한), dropped_iterations 11,433
응답:     중앙값 746ms, p95 790ms
```

실제 처리율은 1,189 req/s에서 멈췄다. k6의 VU 상한 900과 응답시간 0.746초의 비(900 / 0.746 ≈ 1,206)와 일치하므로, 이 수치는 서버가 받을 수 있는 최대 처리량이 아니라 "이 부하 도구 설정으로 걸 수 있는 최대 부하"와 서버 포화가 동시에 도달한 값이다. 어느 쪽이든 단일 쿠폰 행의 처리 상한이 이 환경에서 초당 1,200건 안팎임을 뜻한다.

병목이 행 잠금이라는 근거는 잠금 대기 시간이다. 30.8초 동안 잠금 대기 합계가 170.4초이므로, 평균 5.5개의 트랜잭션이 항상 잠금을 기다리고 있었다. 사용 중인 커넥션 10개 중 절반 이상이 행 잠금 대기에 쓰인 것이다. 모든 요청(100%)이 잠금을 기다렸고 대기당 평균 4.7ms였다.

p95는 800에서 7.4ms, 1,600에서 790ms로 100배 이상 늘었다.

### 관찰 3. 정상 상태에서도 한 번의 정지가 전체를 멈춘다

400과 800 실행 모두, 그리고 400 재실행에서도 시작 9~14초 뒤에 정확히 한 번 다음 상태가 1~2초 지속됐다.

```text
active=10, pending=118~189, k6 VU 급증 (400 1회차: 2 → 455)
```

`pending` 189는 Tomcat 스레드 200개가 전부 막힌 상태다. 정지가 길었던 400 1회차는 최대 2.02초, p95 772ms를 남겼고, 짧았던 800은 최대 0.66초로 p95에는 잡히지 않았다.

정지의 원인은 확인하지 않았다. GC, JIT 컴파일, InnoDB 플러시, 운영체제 어느 것도 배제하지 못한다. 확인된 것은 결과의 형태다. 같은 행을 순서대로 갱신하는 구조에서는 잠금 보유자가 잠시 멈추면 뒤의 요청 전부가 그 뒤에 쌓이고, 커넥션 풀과 Tomcat 스레드가 차례로 소진된다. 정상 상태의 3ms짜리 요청이 2초가 된다.

### 재현 판단

[V4 개발 가이드](development-guide.md)에 미리 정한 기준과 대조한다.

| 기준 | 결과 |
|---|---|
| 도착률을 두 배로 올렸을 때 p95가 두 배 이상 | 충족. 800 → 1,600에서 7.4ms → 790ms |
| HikariCP `pending`이 실행 중 지속적으로 0보다 큼 | 충족. 1,600에서 30초 내내 188~189 |
| `Innodb_row_lock_time_avg`가 도착률에 비례해 증가 | 충족. 대기당 1.3ms (800) → 4.7ms (1,600) |
| 커넥션 획득 실패 또는 Lock wait timeout으로 HTTP 500 | 미충족. 최대 대기 1.22초로 타임아웃(30초, 50초)에 이르지 않음 |

네 기준 중 셋을 충족했다. **V3의 DB 행 경합 문제는 재현됐다.** 이 환경에서 단일 쿠폰의 동기 발급은 초당 약 1,200건에서 포화되고, 그 지점부터 응답시간이 100배로 뛴다. 정상 범위 안에서도 한 번의 정지가 전체 스레드를 소진시키는 취약성이 있다.

### 측정하지 않은 것과 한계

- 3,200 req/s는 실행하지 않았다. 1,600에서 k6와 서버가 동시에 포화돼 더 올려도 드롭만 늘어난다.
- 병목이 행 잠금인지 CPU인지 완전히 분리하지 못했다. 세 프로세스가 한 대에서 도는 환경이므로, 잠금 대기 시간 비중(커넥션 시간의 절반 이상)을 근거로 행 잠금을 주된 원인으로 판단했다.
- 정지 원인은 확인하지 않았다. GC 로그와 InnoDB 상태를 함께 기록하면 좁힐 수 있다.
- V2로 같은 실험을 반복하지 않았다. V3에서 재현됐고 V2는 잠금 구간이 더 길어 같은 문제가 더 일찍 나타날 것이 분명하다.
- 1,600에서 관찰 스크립트의 샘플 간격이 2초로 벌어졌다. Actuator 응답도 같은 Tomcat 스레드를 쓰므로 함께 느려진 것이다.

### 결과에서 제외한 실행

- 도착률 100 실행의 잠금 대기 668회: 재시작 직후 예열 효과가 섞여 있어 정상 상태 비교에서 제외한다. p95 9.36ms는 참고로 남긴다.

## 2부. V4 Redis 비교

### 실험 개요

- 실험일: 2026-09-17
- 대상 구현: `coupon.service.v4.V4CouponIssueService` (`coupon.issue.version=v4`)
- 비교 대상: 같은 날 다시 측정한 V3. **1부 수치는 비교에 쓰지 않는다.** 이유는 아래 "1부와 비교할 수 없는 이유"에 있다.
- 부하 도구, 관측 도구, 애플리케이션, 데이터베이스는 1부와 같다.
- Redis: `redis:7` (7.4.11), Docker Desktop, `maxmemory-policy noeviction`, 호스트에서 포트 6379로 접근

### 조건

- V4는 쿠폰 155(재고 1,000,000), V3 재측정은 쿠폰 190(재고 1,000,000). 구현마다 새 쿠폰을 쓴 이유는 V4가 `coupon.remaining_quantity` 를 갱신하지 않아 한 쿠폰에 두 구현의 흔적이 섞이면 사후 검증이 무의미해지기 때문이다.
- 도착률 400, 800. 각 30초.
- 사후 검증은 `snapshot.ps1 -CouponId` 가 Redis 재고 키의 유무로 잔여 수량을 어디서 읽을지 스스로 정한다. V4 쿠폰은 `remaining=...(redis)`, V3 쿠폰은 `remaining=...(db)` 로 찍힌다.
- V4는 `SCARD issued` 와 발급 이력 수의 차이(`issued_gap`)도 함께 확인한다.

### 같은 날 비교 (2026-09-17)

| 도착률 | 구현 | 요청 수 | 실패 | 실제 처리율 | 중앙값 | p95 | 최대 | 잠금 대기 횟수 (비율) | 잠금 대기 합계 | 실행 중 `active` / `pending` |
|---:|---|---:|---:|---:|---:|---:|---:|---:|---:|---|
| 400 | V3 | 12,001 | 0 | 399.9 | 6.9ms | 36.76ms | 850ms | 2,599 (21.7%) | 12,194ms | 정지 1회: 10 / 189, 그 외 1~3 / 0 |
| 400 | **V4** | 12,001 | 0 | 399.9 | **6.78ms** | **13ms** | **106ms** | **0** | **0ms** | **1~4 / 0 (30초 내내)** |
| 800 | V3 | 18,221 | 0 | 580.6 | 1.41s | 2.24s | 3.91s | 18,215 (100%) | 186,086ms | 9~10 / 188~189 (30초 내내) |
| 800 | **V4** (풀 10) | 20,316 | 275 | 651.1 | 1.05s | 2.06s | 4.46s | **0** | **0ms** | 8~10 / 177~190 (30초 내내) |
| 800 | **V4** (풀 50) | 18,236 | 0 | 583.1 | 1.34s | 2.53s | 5.57s | **0** | **0ms** | 38~50 / 147~149 (30초 내내) |

모든 실행에서 HTTP 500은 0건이었다. V4 실행의 사후 검증은 전부 `consistency_gap=0`, `issued_gap=0` 이었다. 800 포화 상태에서 요청 수천 건이 1초 넘게 밀리고 5,765건이 드롭된 실행에서도 Redis 재고와 `coupon_issue` 행 수가 한 건도 어긋나지 않았다.

### 관찰 1. 행 잠금 경합은 사라졌다

V4는 다섯 번의 실행에서 `Innodb_row_lock_waits` 증가분이 **모두 0** 이었다. 같은 날 V3는 400에서 요청의 21.7%, 800에서 **99.97%** 가 행 잠금을 기다렸다.

`coupon_issue` INSERT 는 외래 키 확인 때문에 여전히 `coupon` 행을 잠그지만 그것은 공유 잠금이라 서로 막지 않는다. V3의 조건부 UPDATE 는 배타 잠금이라 한 번에 하나만 통과시켰다. 그 차이다.

### 관찰 2. 한 번의 정지가 전체를 멈추는 현상이 없어졌다

도착률 400에서 V3의 관찰 기록에 정지가 그대로 찍혔다.

```text
12:39:45  active=10  pending=189
12:39:46  active=2   pending=0
12:39:47  active=3   pending=0
```

1초 동안 커넥션 10개가 모두 차고 189개가 줄을 섰다. 이 한 번이 V3의 p95를 36.76ms, 최대를 850ms로 끌어올렸다. 중앙값은 6.9ms였으므로 정지가 없었다면 꼬리도 짧았을 것이다.

같은 30초 동안 V4의 `pending` 은 한 번도 0을 벗어나지 않았고 `active` 는 최대 4였다. 정지가 와도 쌓일 곳이 없다. 모두가 기다리던 그 행을 V4는 건드리지 않기 때문이다.

이것이 가설에서 "호송 현상이 약해진다" 고 적은 부분이며, 400 구간에서 V4의 p95가 2.8배, 최대가 8배 나은 이유다.

### 관찰 3. 포화 지점은 올라가지 않았다

가설의 세 번째 주장은 확인되지 않았다. 도착률 800에서 V3는 580.6/s, V4는 583~651/s 로 **둘 다 같은 자리에서 막혔다.** 행 잠금을 완전히 없앴는데도 총 처리량이 늘지 않았다.

병목이 행 잠금이 아닌 다른 곳으로 옮겨갔다는 뜻이다. 그곳이 어디인지는 이 실험으로 좁히지 못했다. 다만 커넥션 풀은 아니다. 풀을 10에서 50으로 다섯 배 늘렸을 때 처리율이 651/s 에서 583/s 로 **오히려 떨어졌다.**

| 풀 크기 | 처리율 | 커넥션당 점유 시간 (풀 / 처리율) |
|---:|---:|---:|
| 10 | 651/s | 15.4ms |
| 50 | 583/s | 85.8ms |

동시성을 다섯 배로 올렸더니 일 하나당 걸리는 시간이 5.6배가 되고 총 처리량은 그대로였다. 풀 아래쪽의 공유 자원이 이미 포화라는 신호다. 애플리케이션, MariaDB, Redis 컨테이너, k6 가 모두 한 대에서 도는 환경이므로 CPU 가 가장 유력하지만 확인하지 않았다.

Redis 왕복 자체는 범인이 아니다. 애플리케이션이 실제로 타는 경로(호스트 → Docker 포트포워딩 → Redis)로 PING 을 2,000회 측정한 결과 중앙값 0.47ms, p95 0.99ms, p99 1.58ms 였다. 요청당 한 번 왕복하므로 0.5ms 안팎이며, 400 구간에서 두 구현의 중앙값 차이(6.9ms 대 6.78ms)가 그보다도 작다.

### 1부와 비교할 수 없는 이유

2부를 쓰면서 V3를 다시 측정한 것은 1부 수치를 그대로 쓸 수 없다고 판단했기 때문이다. 근거는 같은 V3 를 같은 조건으로 다시 돌린 결과다.

| V3 @ 800 | 1부 (2026-09-15) | 2부 재측정 (2026-09-17) |
|---|---:|---:|
| 실제 처리율 | 799.9/s | 580.6/s |
| 중앙값 | 3.59ms | 1.41s |
| p95 | 7.43ms | 2.24s |
| 실행 중 `pending` | 정지 1회만 189 | 30초 내내 188~189 |

코드도 조건도 같은데 중앙값이 390배가 됐다. 이틀 사이에 실행 환경이 달라졌다는 뜻이며, 그렇다면 1부의 V3 수치와 오늘의 V4 수치를 나란히 놓는 비교는 성립하지 않는다.

의심되는 원인은 Docker Desktop 이다. 1부 시점에는 Redis 를 쓰지 않아 꺼져 있었고 지금은 V4 때문에 상시 떠 있다. Windows 에서 Docker Desktop 은 리눅스 VM 을 띄워 CPU 와 메모리를 계속 점유한다. 확인하지는 않았다.

이것은 이 프로젝트의 구조적 한계이기도 하다. **V4 를 측정하려면 Docker 가 켜져 있어야 하는데, Docker 를 켜는 것 자체가 환경을 바꾼다.** 컴퓨터 한 대에서 V3 와 V4 를 완전히 동등한 조건으로 비교할 수 없다. 2부의 비교를 같은 날 같은 세션 안에서 수행한 이유가 이것이다.

### 측정하지 않은 것과 한계

- 도착률 1,600 은 실행하지 않았다. 오늘 환경에서는 두 구현 모두 600/s 부근에서 막히므로 더 올려도 양쪽이 더 깊이 무너지는 것만 보인다. 1부가 3,200 을 건너뛴 것과 같은 이유다.
- 800 을 막는 새 병목이 무엇인지 좁히지 못했다. 커넥션 풀이 아니라는 것과 Redis 왕복이 아니라는 것까지만 확인했다. GC 로그, CPU 사용률, MariaDB 의 커밋 fsync 를 함께 기록하면 좁힐 수 있다.
- V4 발급 트랜잭션은 Redis 왕복 동안 DB 커넥션을 쥐고 있다. 공통 규칙("발급 전체를 하나의 `@Transactional` 메서드로 묶는다")을 따른 결과다. 오늘 환경에서는 이것이 병목이 아니었지만(풀을 늘려도 처리율이 안 올랐다) Redis 가 느린 환경에서는 문제가 될 수 있다.
- V4 의 800 풀 10 실행에서 시작 1초 안에 275건의 TCP 연결 거절이 났다. 응답이 느려 k6 가 VU 를 900개까지 올리면서 동시에 연결을 열었기 때문이며, 1부의 1,000 VU 실험에서 본 로컬 HTTP 진입 한계와 같은 현상이다. 이 실행의 처리율은 그만큼 부풀려 읽지 않는다.
- 각 조건을 한 번씩만 측정했다. 400 은 V4 를 두 번 돌려 재현을 확인했지만 800 은 그러지 못했다.
